Running it on one computer (e.g. a 42 machine)

Companion to architecture.html, which shows production on solsys. Here everything runs on the one computer: Docker for our four containers (WAF ×2, frontend, backend) plus a dev-mode Vault, and the Supabase CLI for a local copy of Supabase (Auth, Realtime, Postgres, a mail catcher). Nothing goes to solsys or ft.natscho.my, and with make local nothing touches production data either. The only things that can leave the machine are optional: Google sign-in, and the shared .env route in red below. Part 2 shows the setup since the Vault switch (13 Oct), where the secrets come from the Vault on solsys instead of a .env file.

What happens, in order

0

At boot the backend reads its secrets (JWT secret, Supabase keys, database URL, SMTP) from the local dev-mode Vault, which vault-init.sh filled from your .env a moment earlier. Not the Vault on solsys.

1

Chrome opens https://localhost:8443. The WAF checks the request and passes it to the frontend on :3000.

2

Signing in goes straight from Chrome to local Supabase Auth on 127.0.0.1:54321 (email + password; Google only if its keys are set). The Realtime WebSocket (who's online, live notices) uses the same port.

3

Every API call goes to https://localhost:9443/api: the second WAF, then the backend on :4000. The first call trades the Supabase token for our own login token.

4

The backend checks that Supabase token with local Supabase Auth, through host.docker.internal:54321 (inside a container, 127.0.0.1 is the container itself).

5

All data goes to the local Postgres on host.docker.internal:54322: test data only, gone when you run supabase stop --no-backup.

6

Emails (feedback, role and suspension notices, tree deleted) land in Mailpit: open http://127.0.0.1:54324 to read them.

On a 42 machine

✅
First time, step by step
  1. Docker running. If your home folder has a small quota, keep Docker's data in your goinfre: the images need a few GB.
  2. The Supabase CLI (or use npx supabase wherever the steps say supabase).
  3. make local: makes the certificates, starts local Supabase, starts our containers, and pushes the database schema (from inside the backend container, so no Node needed on the machine).
  4. Open https://localhost:9443/api once and accept the certificate warning, then https://localhost:8443 and accept it again.
  5. Sign up a test user. The confirmation email (if any) is in Mailpit.
⚠️
No admin rights: the certificate warnings. make certs uses mkcert when it's installed, but trusting mkcert's certificates usually needs admin rights. Without it, the Makefile makes a self-signed certificate and Chrome warns on both ports. If you only accept :8443, the page loads but every API call to :9443 fails quietly and login looks broken. Accept :9443 too (step 4).
⚠️
Since the Vault switch (part 2, 13 Oct). With VAULT_USER set, a team member's make up fetches the secrets from the Vault on solsys through their own SSH tunnel (no admin rights needed) and works on the production Supabase. Evaluators on their own don't set VAULT_USER: make up then reads .env, and make local stays the safe choice (local Vault, local Supabase).

2 · Since the Vault switch (13 Oct; on tching-solsys, not on branchsaurus yet)

For team members. Same make up as part 1, with one difference: the secrets no longer sit in a .env file. With VAULT_USER set, make up opens the person's own SSH tunnel through the GCP proxy (public IP) to the Vault on solsys (the Vault server, HashiCorp Vault), reads the dev secrets into memory for that one run, and starts the whole stack locally on the production Supabase (decided 12 Oct). solsys only hands out secrets: the build and the running app stay on the computer, and the production stack can't be reached from it.

1

make up opens the person's own SSH tunnel (their account on the GCP proxy can only forward to 10.8.0.1:8200), checks Vault answers and is unsealed, then logs in with the person's own Vault password (once a day; the token is kept in ~/.vault-token, owner-only) and reads secret/family-tree/dev. Vault records the read in its audit log.

2

The dev secrets come back into memory only, for this one command: the production Supabase URLs and service key, a JWT_SECRET of their own (a laptop login isn't valid on ft.natscho.my) and no email password. No file is written. A teammate's login can't read …/prod: Vault answers 403.

3

The same stack as part 1 starts with them: both WAFs, frontend, backend and a local dev-mode Vault, which vault-init.sh fills from memory.

4

Chrome opens https://localhost:8443: every page and API call goes through the local WAFs first (:8443 pages, :9443 API), the same ModSecurity rules as production.

5

The backend, and Chrome for sign-in and Realtime, use the production Supabase: the real accounts and the real users' data. Test on your own test trees and accounts.

⚠️
When the Vault route can't be used
  • No key yet or tunnel refused: make up stops with “SSH tunnel failed. Has Tiara added your SSH key?”. Unset VAULT_USER to run from .env, or use make local (local Supabase, test data).
  • solsys restarted: Vault is sealed until 2 of the 5 share holders run make unseal (solsys adds its own share by itself, so one teammate is enough).
  • solsys, home internet or the GCP proxy down: same fallback; the live site is down too in that case.
  • Checked 13 Oct: outgoing SSH (port 22) to ft.natscho.my works from the 42 campus network (u80z04s04). On a new machine the first connection asks to confirm the server's key: accept only SHA256:teGq/ElfqZAFyQoJ04Q7Z6fZbKrYtYXOcgr10b077Bg.
  • make up skips Vault (“from the environment: (none)”, then “JWT_SECRET is empty”): VAULT_USER isn't set in that terminal. Run VAULT_USER=<login> VAULT_SSH_KEY=~/.ssh/ft_vault make up, or reload ~/.zshrc.
  • Found on the first 42 run, fixed 13 Oct: the WAFs crash-looped on the 0600 TLS key (make certs now makes it readable, c246fe4), and the frontend WAF blocked the canvas page's chunk at paranoia level 2 (rule 932130 on [id]; a narrow exclusion under /_next/static/, fda4dbf).
