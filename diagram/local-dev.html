Running it on one computer (e.g. a 42 machine)

Companion to architecture.html, which shows production on solsys. Here everything runs on the one computer: Docker for our four containers (WAF ×2, frontend, backend) plus a dev-mode Vault, and the Supabase CLI for a local copy of Supabase (Auth, Realtime, Postgres, a mail catcher). Nothing goes to solsys or ft.natscho.my, and with make local-security nothing touches production data either. The only things that can leave the machine are optional: Google sign-in, and the shared .env route in red below.

What happens, in order

0

At boot the backend reads its secrets (JWT secret, Supabase keys, database URL, SMTP) from the local dev-mode Vault, which vault-init.sh filled from your .env a moment earlier. Not the Vault on solsys.

1

Chrome opens https://localhost:8443. The WAF checks the request and passes it to the frontend on :3000.

2

Signing in goes straight from Chrome to local Supabase Auth on 127.0.0.1:54321 (email + password; Google only if its keys are set). The Realtime WebSocket (who's online, live notices) uses the same port.

3

Every API call goes to https://localhost:9443/api: the second WAF, then the backend on :4000. The first call trades the Supabase token for our own login token.

4

The backend checks that Supabase token with local Supabase Auth, through host.docker.internal:54321 (inside a container, 127.0.0.1 is the container itself).

5

All data goes to the local Postgres on host.docker.internal:54322: test data only, gone when you run supabase stop --no-backup.

6

Emails (feedback, role and suspension notices, tree deleted) land in Mailpit: open http://127.0.0.1:54324 to read them.

On a 42 machine

✅
First time, step by step
  1. Docker running. If your home folder has a small quota, keep Docker's data in your goinfre: the images need a few GB.
  2. The Supabase CLI (or use npx supabase wherever the steps say supabase).
  3. make local-security: makes the certificates, starts local Supabase, starts our containers, and pushes the database schema (from inside the backend container, so no Node needed on the machine).
  4. Open https://localhost:9443/api once and accept the certificate warning, then https://localhost:8443 and accept it again.
  5. Sign up a test user. The confirmation email (if any) is in Mailpit.
⚠️
No admin rights: the certificate warnings. make certs uses mkcert when it's installed, but trusting mkcert's certificates usually needs admin rights. Without it, the Makefile makes a self-signed certificate and Chrome warns on both ports. If you only accept :8443, the page loads but every API call to :9443 fails quietly and login looks broken. Accept :9443 too (step 4).
⚠️
After the Vault switch (planned after 24 Oct). make up will fetch the dev secrets from the Vault on solsys over WireGuard. Installing WireGuard needs admin rights, so on a 42 machine keep using make local-security (local Vault, local Supabase), which needs neither.
✅
Evaluation note: one command. The subject asks for one command to run the project. make local-security is that command without touching production data: since 11 Oct it also pushes the schema into the empty local database, so a fresh machine needs only Docker and the Supabase CLI.
