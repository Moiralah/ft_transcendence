Secrets in Vault: how it all ties together

Every secret lives only in Vault on solsys (the Vault server, HashiCorp Vault). Each teammate reaches it through their own SSH tunnel via the GCP proxy (public IP), then builds and runs the app on their own laptop with make up (at https://localhost:8443, both WAFs, on the production Supabase), and make deploy updates https://ft.natscho.my. Both get the secrets from Vault; no secret file is kept anywhere.

2 · The commands

Same names the team already uses, so habits don't change; make deploy and make unseal are new. Without VAULT_USER, make up takes the values from .env instead (evaluators, 42 machines, or when Vault is down).

Anyone · on their laptop

make up

  1. Opens your own SSH tunnel (127.0.0.1:18201 → your GCP account → 10.8.0.1:8200)
  2. Logs you in to Vault if today's token expired (your login + password)
  3. Fetches the dev secrets into memory: the production Supabase keys, a JWT secret of their own, no email password
  4. Builds and starts the app, both WAFs and the local Vault

→ the app at https://localhost:8443 (API :9443). make down stops it; the secrets go with it. Tested 11 Oct: the tunnel accounts (no shell, only the Vault forward). 13 Oct: the full run on a 42 machine (u80z04s04) as tching: tunnel, password, dev secrets, app at :8443.

Tiara · from a laptop with ssh to solsys

make deploy

  1. Connects to solsys (ssh solsys) and pulls the latest branchsaurus
  2. Runs make prod there: builds, adds solsys's share if Vault is sealed, and stops without touching the live site if it is still sealed
  3. Starts the production stack (the backend logs in to Vault with its AppRole), restarts the WAFs
  4. Checks it: pages 200, API 401

→ https://ft.natscho.my is updated and checked, in one command.

Any share holder · only after solsys reboots

make unseal

  1. Runs on your own laptop, through your SSH tunnel (no account on solsys needed)
  2. You type your share (hidden, never stored)
  3. solsys adds its own share by itself (a job that checks every minute)
  4. 2 of 5 shares → Vault unlocks; the backend reconnects on its own

→ while sealed, pages load but the API is down (nobody can log in), and make up stops. Rehearsed: the API was back 6 s after the second share, with no redeploy.

5 · Decisions (8, 11 and 12 Oct)

🧭
Access path: an SSH tunnel per person (11 Oct; was WireGuard on each laptop). Vault is never on the internet. Each person has their own account on the GCP proxy (public IP), named like their Vault login, that can only forward to Vault on solsys: no shell, no password, key file owned by root. No admin rights or VPN install needed; make up opens the tunnel by itself. Nobody has an account on solsys.
🧪
Laptops use the production Supabase (12 Oct; was a local Supabase on each laptop). secret/family-tree/dev holds the same database URLs, auth URL and service key as production, with its own JWT_SECRET (a login made on a laptop isn't valid on ft.natscho.my) and no SMTP_PASS (laptops never email real users). The accepted cost: every teammate's run works on the real users' data, and the service key bypasses row-level security. Mitigations: values in memory only, every read in Vault's audit log, test on your own test trees and accounts, and a backup before risky tests. make local (local Supabase, test data) stays as an option.
🔑
Unseal: 5 shares (Tiara, solsys, Yiwei, Jon, Moira), any 2 unlock. After a reboot, solsys adds its own share, so any one teammate can bring Vault back alone: convenient, no waiting for a second person. The accepted cost: solsys's share sits on the same machine as the encrypted data, so someone who gets into solsys and obtains one person's share could unlock everything. Mitigations: solsys's share is an owner-only file (~/.ft-vault/unseal-share) outside Vault's data, each person keeps their share offline, and every unseal is logged.
🛟
Evaluation-day fallback. If solsys or the home internet fails during the evaluation, both the live site and every Vault-backed make up stop. make up without VAULT_USER still runs the app from a local .env (as evaluators will); keep a sealed, offline copy of what's needed for the demo (held by Tiara).
