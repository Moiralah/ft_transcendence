Secrets in Vault: how it all ties together

Every secret lives only in Vault on solsys. Teammates build and run the app on their own laptop with make up (at https://localhost:3000, on a local Supabase), and make deploy updates https://ft.natscho.my. Both get the secrets from Vault; no secret file is kept anywhere.

2 · The commands

Same names the team already uses, so habits don't change; make deploy and make unseal are new. make up-env keeps the old way (values from .env) for when Vault or WireGuard is down.

Anyone · on their laptop

make up

  1. Checks WireGuard is on (Vault reachable at 10.8.0.1:8200)
  2. Logs you in to Vault if today's token expired (your username + password)
  3. Fetches the dev secrets into memory (laptops can't read production)
  4. Builds and starts the app with them, on local Supabase

→ the app at https://localhost:3000. make down stops it; the secrets go with it. Rehearsed as Moira: the backend's JWT_SECRET came from Vault, not from .env.

Tiara · from a laptop with ssh to solsys

make deploy

  1. Connects to solsys (ssh solsys) and pulls the latest branchsaurus
  2. Runs make prod there: builds, adds solsys's share if Vault is sealed, and stops without touching the live site if it is still sealed
  3. Starts the production stack (the backend logs in to Vault with its AppRole), restarts the WAFs
  4. Checks it: pages 200, API 401

→ https://ft.natscho.my is updated and checked, in one command.

Any share holder · only after solsys reboots

make unseal

  1. Runs on your own laptop, through WireGuard (no ssh to solsys needed)
  2. You type your share (hidden, never stored)
  3. solsys adds its own share by itself (a job that checks every minute)
  4. 2 of 5 shares → Vault unlocks; the backend reconnects on its own

→ while sealed, pages load but the API is down (nobody can log in), and make up stops. Rehearsed: the API was back 6 s after the second share, with no redeploy.

5 · Decisions (2026-10-08)

🧭
Access path: A · WireGuard. Vault is never on the internet; each teammate gets a personal WireGuard key (one-time setup) and turns it on before make up. To check first: that WireGuard works from the 42 campus network.
🧪
Laptops get a separate dev set, on local Supabase. First planned as a second cloud project; changed the same day to a local Supabase on each laptop (no cost, never paused, works offline). Its keys are public defaults, so secret/family-tree/dev only holds what is really secret (today JWT_SECRET). Laptops can't read secret/family-tree/prod, so a lost laptop or a local test can never touch production.
🔑
Unseal: 5 shares (Tiara, solsys, Yiwei, Jon, Moira), any 2 unlock. After a reboot, solsys adds its own share, so any one teammate can bring Vault back alone: convenient, no waiting for a second person. The accepted cost: solsys's share sits on the same machine as the encrypted data, so someone who gets into solsys and obtains one person's share could unlock everything. Mitigations: solsys's share is an owner-only file (~/.ft-vault/unseal-share) outside Vault's data, each person keeps their share offline, and every unseal is logged.
🛟
Evaluation-day fallback. If solsys or the home internet fails during the evaluation, both the live site and every make up stop. make up-env still runs the app from a local .env; keep a sealed, offline copy of what's needed for the demo (held by Tiara).
