How the services talk to each other

The browser talks to two different backends for auth — Supabase directly, then our own API — which is the part that trips people up. Everything else is one path: browser → our backend → Postgres.

Browser Supabase Auth Backend (NestJS) Postgres External OAuth (optional)
1

Browser → Supabase Auth — signInWithPassword() or signInWithOAuth(), called directly from the frontend. Our backend isn't involved yet.login only

↳

Supabase Auth ↔ Google/GitHub — only for OAuth sign-in: Supabase redirects to the provider, gets consent, provider redirects back to Supabase's own fixed callback URL. The browser never talks to Google/GitHub directly.OAuth only

2

Supabase Auth → Browser — returns a Supabase-issued access token/session. Not our app's session yet.login only

3

Browser → Backend — POST /api/auth/login { accessToken }, exchanging the Supabase token for our own session.login only

4

Backend → Supabase Auth — supabase.auth.getUser(accessToken) to verify the token is real before trusting it.login only

5

Backend ↔ Postgres — via Prisma: find-or-create the local User, check role and twoFactorEnabled.login only

6

Backend → Browser — issues our own app JWT (with role baked in), or a short-lived 2FA challenge token if 2FA is on.login only

7

Browser → Backend, every request after this — Authorization: Bearer <app JWT> straight to the backend for trees, profiles, admin actions, 2FA settings. Supabase isn't in the loop at all anymore.ongoing

⚠️
Local dev gotcha: when the backend runs in Docker and Supabase runs locally on the host, 127.0.0.1 inside the container means the container itself, not your machine — steps 4 and 5 silently fail if SUPABASE_AUTH_URL/DATABASE_URL aren't set to host.docker.internal instead. See README → Running Supabase Locally for the full fix — this one bug alone caused most of the auth failures debugged this session.
