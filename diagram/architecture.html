How the services talk to each other

The browser talks to two different backends for auth — Supabase directly, then our own API through a WAF — which is the part that trips people up. It also keeps one more direct line to Supabase open: a Realtime WebSocket for who's online in a tree and live change notices. Everything else is one path: browser → WAF → our backend → Postgres (when run with make security, at https://localhost:8443; plain make up has no WAF). In production there's one extra hop in front: a GCP VM terminates HTTPS and forwards over a WireGuard tunnel to the home server solsys, where the containers run. Separately, the backend pulls its own secrets from Vault once at boot, before any of that.

Browser WAF (ModSecurity) Vault (secrets) Supabase (Auth + Realtime) Backend (NestJS) Postgres External: Google OAuth, Gmail SMTP
0

Backend → Vault — at boot, before it accepts any requests: logs in via AppRole (VAULT_ROLE_ID/VAULT_SECRET_ID), reads secret/data/family-tree/backend, injects its 6 secrets (JWT_SECRET, DATABASE_URL, SMTP_PASS…) into its own process.env. They are not in the container's environment at all. One-time, not part of the request flow — everything below still works the same either way.boot only

1

Browser → Supabase Auth — signInWithPassword() or signInWithOAuth(), called directly from the frontend. Neither our backend nor our WAF are involved yet.login only

↳

Supabase Auth ↔ Google — only for OAuth sign-in: Supabase redirects to Google, gets consent, Google redirects back to Supabase's own fixed callback URL. (GitHub was built and then dropped.)OAuth only

2

Supabase Auth → Browser — returns a Supabase-issued access token/session. Not our app's session yet.login only

3

Browser → WAF → Backend — POST /api/auth/login { accessToken } via the WAF on :9443 (in production: https://ft.natscho.my/api/auth/login, no port, through the GCP proxy and WireGuard tunnel first), exchanging the Supabase token for our own session. ModSecurity inspects the request before it reaches NestJS.login only

4

Backend → Supabase Auth — supabase.auth.getUser(accessToken) to verify the token is real before trusting it.login only

5

Backend ↔ Postgres — via Prisma: find-or-create the local User, check role and twoFactorEnabled.login only

6

Backend → Browser — issues our own app JWT (with role baked in), or a short-lived 2FA challenge token if 2FA is on. Flows back through the same WAF connection.login only

7

Browser → WAF → Backend, every request after this — Authorization: Bearer <app JWT> for trees, profiles, friends, admin actions, 2FA settings, feedback — same WAF-fronted path as step 3. Supabase Auth isn't in the loop at all anymore.ongoing

R

Browser ↔ Supabase Realtime — a WebSocket straight from the frontend to Supabase (useTreePresence: who's on the same tree canvas; notification.ts: toasts on new AuditLog rows). Not through the GCP proxy or our WAF; the page's CSP allows it explicitly.while a tree is open

F

Backend → Gmail SMTP — the public /feedback form (honeypot + rate limit) is emailed to the team over STARTTLS on :587, with the app password from Vault.feedback only

Since 2026-10-06 both WAFs run OWASP CRS at paranoia level 2 in blocking mode (one day in detection mode first, checked with waf/pl2-report.sh). The API WAF only accepts application/json, with bodies up to 1 MB. Tuning, backend WAF only, in waf/backend-exclusions.conf: PUT/PATCH/DELETE allowed (rule 911100), the JSON field profileId (rule 930120), and rule 1000030, which skips 942440 (a plain --) and 932236 (a person called "Local") on free-text fields only. Values are still inspected and every other rule still applies; waf/test-waf.sh checks 21 cases.
🔀
How the app actually reaches the WAF: the browser calls the API directly (not through the frontend), so putting a WAF in front of the frontend alone would inspect none of it. In the security stack docker-compose-security.yml therefore sets NEXT_PUBLIC_API_URL=https://localhost:9443/api on the frontend and CORS_ORIGIN=https://localhost:8443 on the backend, and Supabase's redirect allowlist includes https://localhost:8443 for OAuth. Open the app on :8443; on :3000 its API calls fail CORS. make up and .env are unchanged.
🔐
Vault proven working too: docker logs transpeed-backend-1 | grep vault shows [vault] loaded 6 secrets from secret/data/family-tree/backend, and a real login (which needs the Vault-sourced DATABASE_URL and SUPABASE_AUTH_URL to work) succeeds — not just that the values loaded, that the app actually functions on them. AppRole token confirmed scoped to read-only on that one path (denied on sys/mounts). Since 2026-10-06 the secrets reach the backend only through Vault: they are blanked in the container's environment (docker inspect shows them empty), and vault-init.sh revokes every older AppRole secret_id on each run.
⚠️
Vault is dev mode — resets on every restart: in-memory only, no storage backend, unsealed automatically with a hardcoded root token. That's why make security runs scripts/vault-init.sh every time rather than once — the secret, the AppRole, and its policy are all gone the moment the vault container restarts, and get rebuilt from scratch — seeded from .env, which is still required. A real deployment needs persistent storage (file/Raft), TLS, and proper unsealing instead. That replacement is built and rehearsed (branch tching-cybersec, vault/README.md): server mode with file storage, 5 unseal shares of which any 2 open it, a login per teammate, an audit log, and no root token. It goes live on solsys after the evaluations (after 24 Oct).
🔒
WAF is the only way in (security stack): :3000/:4000 are no longer published — ports: !reset [] on backend/frontend in docker-compose-security.yml, so a WAF with a bypass path is no longer the situation. The WAFs still reach them over the Docker network. Plain make up has no WAF and keeps publishing them. The !reset tag needs Docker Compose 2.24 or newer.
⚠️
Local dev gotcha (bit us three times this project): when the backend runs in Docker and Supabase runs locally on the host, 127.0.0.1 inside the container means the container itself, not your machine — steps 4 and 5 silently fail if SUPABASE_AUTH_URL/DATABASE_URL aren't set to host.docker.internal instead. Any docker compose up that touches backend — including just bringing the WAF up, via depends_on — can silently reset this. See README → Running Supabase Locally for the full fix.
🌐
Live in production (moved 2026-10-04): the same architecture now runs on a home server, solsys, instead of the free-tier GCP e2-micro, which couldn't build the images reliably. The GCP VM is the public entry point, and since the same day the site has no port: https://ft.natscho.my, with the API at https://ft.natscho.my/api. GCP's nginx terminates HTTPS on the normal port 443 with the real Let's Encrypt cert and picks a WAF by path (/api → solsys :9443, everything else → :8443) over a WireGuard tunnel (GCP 10.8.0.2 ⇄ solsys 10.8.0.1). Pages and API share one origin, so CORS_ORIGIN is https://ft.natscho.my. The old :8443/:9443 URLs 308-redirect to the new address. GCP runs no Docker at all (removed 2026-10-09); its cert-renewal hook just reloads nginx. In front of the tunnel the GCP nginx rate-limits the API (10 requests/s per IP, burst 40) and login and feedback (30/min), sends the security headers and a CSP, and CrowdSec and fail2ban ban abusive addresses; natscho.my is DNSSEC-signed (since 2026-10-06). On solsys the WAFs are published on the tunnel address only, so not even the home LAN can bypass the proxy. Verified over the public internet: 
https://ft.natscho.my/login                         → 200
https://ft.natscho.my/api/trees/my-trees           → 401 (reaches the real app, unauth'd)
SQLi payload via /api                              → 403 (solsys WAF blocking it)
https://ft.natscho.my:8443/login                   → 308 → https://ft.natscho.my/login
backend log: [vault] loaded 6 secrets from secret/data/family-tree/backend
Vault is still bound to loopback only (127.0.0.1:8200): its dev-mode root token is hardcoded in this public repo. On solsys, start the stack with the extra local docker-compose.home.yml, not make prod, which would publish the WAFs on every interface.
📡
Realtime is a second direct path to Supabase (step R): the canvas's presence and the live notifications use a Supabase Realtime WebSocket from the browser, with the public anon key. It doesn't pass the GCP proxy or our WAF, so its protection is Supabase's own (the anon key plus the database's row-level security policies on the tables it streams, such as AuditLog). Worth checking that those policies stop a logged-in user from receiving other trees' changes.
🧱
solsys hardened to the CIS benchmark (2026-10-09/10): 72 of 77 CIS Ubuntu + Docker checks pass. SSH takes keys only, no root, one allowed user; network kernel settings; core dumps off; password quality and lockout for sudo; auditd (52 rules) and AIDE (daily file-integrity check); Docker logs capped at 10 MB × 3 with live-restore, so containers keep running when Docker itself restarts. Single point of failure: the home internet connection. On 2026-10-10 it dropped for about five minutes (17:05–17:10) and the site timed out (504) until it came back; solsys itself never went down.
🩹
Login outage on the first solsys deploy (2026-10-04): every login failed with The column User.suspended does not exist in the current database. The production database had never actually received that column; the old GCP deploys hadn't noticed because they kept running an older image without the suspend code. Fixed with a targeted ALTER TABLE "User" ADD COLUMN IF NOT EXISTS "suspended" BOOLEAN NOT NULL DEFAULT false. A schema diff afterwards showed one extra production column, Tree.slug: Moiralah's tree-slug feature, merged the same day, so production and schema.prisma now match exactly.
🩹
Production outage found and fixed (2026-09-25): every login — Google OAuth and email/password alike — had been failing in production since 2026-09-23, root-caused straight from the backend's own logs: PrismaClientKnownRequestError: The column User.role does not exist in the current database. The deployed backend code (and its generated Prisma Client) already expected the role/2FA/RecoveryCode schema from this project's permissions work, but the real production database had never received the migration. Fixed by running prisma db push against production — purely additive, new nullable/defaulted columns and one new empty table, nothing existing touched — verified afterward via the same logs (errors gone) and a real Google OAuth login succeeding end-to-end.
