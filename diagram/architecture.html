my simple family tree — system overview

How the services talk to each other

The browser talks to two different backends for auth — Supabase directly, then our own API through a WAF — which is the part that trips people up. Everything else is one path: browser → WAF → our backend → Postgres (when run with make security, at https://localhost:8443; plain make up has no WAF). Separately, the backend pulls its own secrets from Vault once at boot, before any of that.

Browser WAF (ModSecurity) Vault (secrets) Supabase Auth Backend (NestJS) Postgres External OAuth (optional)
0

Backend → Vault — at boot, before it accepts any requests: logs in via AppRole (VAULT_ROLE_ID/VAULT_SECRET_ID), reads secret/data/family-tree/backend, injects JWT_SECRET/DATABASE_URL/etc. into its own process.env. One-time, not part of the request flow — everything below still works the same either way.boot only

1

Browser → Supabase Auth — signInWithPassword() or signInWithOAuth(), called directly from the frontend. Neither our backend nor our WAF are involved yet.login only

↳

Supabase Auth ↔ Google/GitHub — only for OAuth sign-in: Supabase redirects to the provider, gets consent, provider redirects back to Supabase's own fixed callback URL. The browser never talks to Google/GitHub directly.OAuth only

2

Supabase Auth → Browser — returns a Supabase-issued access token/session. Not our app's session yet.login only

3

Browser → WAF → Backend — POST /api/auth/login { accessToken } via the WAF on :9443, exchanging the Supabase token for our own session. ModSecurity inspects the request before it reaches NestJS.login only

4

Backend → Supabase Auth — supabase.auth.getUser(accessToken) to verify the token is real before trusting it.login only

5

Backend ↔ Postgres — via Prisma: find-or-create the local User, check role and twoFactorEnabled.login only

6

Backend → Browser — issues our own app JWT (with role baked in), or a short-lived 2FA challenge token if 2FA is on. Flows back through the same WAF connection.login only

7

Browser → WAF → Backend, every request after this — Authorization: Bearer <app JWT> for trees, profiles, admin actions, 2FA settings — same WAF-fronted path as step 3. Supabase isn't in the loop at all anymore.ongoing

Two false positives on normal use were tuned out on the backend WAF only: PUT/PATCH/DELETE are allowed (rule 911100 only permits GET/HEAD/POST/OPTIONS by default), and the JSON field profileId no longer trips rule 930120 (waf/backend-exclusions.conf). Values are still inspected and every other rule still applies.
🔀
How the app actually reaches the WAF: the browser calls the API directly (not through the frontend), so putting a WAF in front of the frontend alone would inspect none of it. In the security stack docker-compose-security.yml therefore sets NEXT_PUBLIC_API_URL=https://localhost:9443/api on the frontend and CORS_ORIGIN=https://localhost:8443 on the backend, and Supabase's redirect allowlist includes https://localhost:8443 for OAuth. Open the app on :8443; on :3000 its API calls fail CORS. make up and .env are unchanged.
🔐
Vault proven working too: docker logs transpeed-backend-1 | grep vault shows [vault] loaded 5 secrets from secret/data/family-tree/backend, and a real login (which needs the Vault-sourced DATABASE_URL and SUPABASE_AUTH_URL to work) succeeds — not just that the values loaded, that the app actually functions on them. AppRole token confirmed scoped to read-only on that one path (denied on sys/mounts).
⚠️
Vault is dev mode — resets on every restart: in-memory only, no storage backend, unsealed automatically with a hardcoded root token. That's why make security runs scripts/vault-init.sh every time rather than once — the secret, the AppRole, and its policy are all gone the moment the vault container restarts, and get rebuilt from scratch — seeded from .env, which is still required. A real deployment needs persistent storage (file/Raft), TLS, and proper unsealing instead.
🔒
WAF is the only way in (security stack): :3000/:4000 are no longer published — ports: !reset [] on backend/frontend in docker-compose-security.yml, so a WAF with a bypass path is no longer the situation. The WAFs still reach them over the Docker network. Plain make up has no WAF and keeps publishing them. The !reset tag needs Docker Compose 2.24 or newer.
⚠️
Local dev gotcha (bit us three times this project): when the backend runs in Docker and Supabase runs locally on the host, 127.0.0.1 inside the container means the container itself, not your machine — steps 4 and 5 silently fail if SUPABASE_AUTH_URL/DATABASE_URL aren't set to host.docker.internal instead. Any docker compose up that touches backend — including just bringing the WAF up, via depends_on — can silently reset this. See README → Running Supabase Locally for the full fix.

Production outage found and fixed (2026-09-25): every login — Google OAuth and email/password alike — had been failing in production since 2026-09-23, root-caused straight from the backend's own logs: PrismaClientKnownRequestError: The column User.role does not exist in the current database. The deployed backend code (and its generated Prisma Client) already expected the role/2FA/RecoveryCode schema from this project's permissions work, but the real production database had never received the migration. Fixed by running prisma db push against production — purely additive, new nullable/defaulted columns and one new empty table, nothing existing touched — verified afterward via the same logs (errors gone) and a real Google OAuth login succeeding end-to-end.
